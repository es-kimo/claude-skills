# 테스트 리뷰

좋은 테스트는 세 가지를 만족한다.

1. **동작이 깨지면 실패한다.** 구현이 틀려도 통과하는 테스트는 없느니만 못하다. 안전하다는 착각을 준다.
2. **동작이 같으면 통과한다.** 리팩터링만 했는데 깨지는 테스트는 리팩터링을 막는다.
3. **읽으면 제품이 보인다.** 테스트 이름만 이어 읽어도 이 모듈이 무엇을 약속하는지 알 수 있다.

## 0. 모드

| 모드 | 대상 | blocking 대상 |
|---|---|---|
| 셀프 체크 | 내가 쓴 테스트 | 고친다 |
| 변경 리뷰 | PR이 추가·수정한 테스트, 그리고 테스트가 없는 새 동작 | 이번 변경이 만든 문제만 |
| 점검 | 디렉터리의 테스트 전체 | 전부. 영향이 큰 순서로 |

## 1. 프로젝트 기준 읽기

`docs/review/testing.md`를 찾는다. 없으면 CLAUDE.md·AGENTS.md가 가리키는 테스트 문서를 쓴다. 거기서 가져올 것:

- **테스트 경계**: 모듈마다 어디를 입력과 출력으로 삼는지 (공개 export, 가짜 서버의 최종 상태, 화면).
- **도우미**: 가짜 외부 시스템, 픽스처 로더, config 빌더. 새 테스트는 이것을 쓴다.
- 금지 사항 (skip, 기대값 수정 등).

기준 문서가 없으면 가장 가까운 기존 테스트 파일을 틀로 삼고, 보고 첫 줄에 "기준 문서 없음"을 적는다.

## 2. 볼 것

### 2-1. 무엇을 단언하나

공개 경계에서 입력에 대한 **관찰 가능한 결과**를 단언해야 한다: 반환값, 가짜 외부 시스템에 남은 최종 상태, 화면에 보이는 것.

구현에 묶인 신호:

- **mock 호출 목록 전체를 순서대로 고정한다.** 요청 횟수가 요구사항이면 횟수만 단언하고, 결과는 가짜 시스템의 최종 상태로 확인한다.
- **결과 객체 전체를 `toEqual`로 고정한다.** 테스트 이름이 말하는 필드만 단언하지 않으면, 필드 하나만 늘어도 관계없는 테스트가 깨진다.
- 내부 함수를 테스트하려고 export했다.
- 사용자가 보지 않는 내부 메시지 문자열을 그대로 단언한다. 판별 값(`reason`, `kind`)으로 단언한다.
- 시간, 랜덤, 네트워크를 고정하지 않았다.

아무것도 검증하지 않는 신호:

- 기대값을 구현과 같은 코드로 계산한다.
- mock이 정답을 그대로 돌려주고, 테스트는 그 값을 돌려받는지만 본다.
- `toBeDefined`, `toBeTruthy`, `not.toThrow`만 있다.
- 픽스처가 없으면 조용히 건너뛰는데, CI에서 그 픽스처가 실제로 받아지는지 확인하지 않았다.

### 2-2. 명세로 읽히나

테스트 이름만 뽑아 읽어 본다.

```bash
git grep -hE "^\s*(describe|test|it)(\.each\(.*\))?\(" -- '<경로>/*.test.*'
```

- 이름이 호출자나 사용자 관점의 동작 문장이어야 한다: "다른 곳에서 먼저 고친 글은 저장을 거부한다" ○ / "savePost 테스트 3" ×.
- 파일을 위에서 아래로 읽으면 핵심 흐름 → 경계 입력 → 오류 순서로 나와야 한다.
- 테스트 하나에 동작 하나. 준비 코드가 길면 이름 있는 도우미로 뺀다.
- 기대값의 숫자와 문자열에 근거가 있다 (주석이나 이름 있는 상수).

### 2-3. 테스트 자체의 유지보수성

- 같은 준비 코드(config 빌더, 가짜 서버 세팅)가 여러 파일에 복사돼 있으면 공용 도우미로 옮긴다. 이미 있는 도우미를 두고 새로 만들었으면 지적한다.
- 가짜 외부 시스템은 요청 기록기가 아니라 **실제 동작의 모형**이어야 한다. 그래야 최종 상태로 단언할 수 있다.
- 경계값은 `test.each` 표로 모은다.
- 무거운 전체 픽스처 테스트는 완료 기준이 요구할 때만 쓴다. 나머지는 최소 입력으로 쓴다.

### 2-4. 빠진 테스트

- 이번 변경의 핵심 동작.
- 기존 동작 유지: 새 옵션을 쓰지 않는 기존 입력의 결과.
- 오류 경로: 호출자가 분기해야 하는 실패.

## 3. 실패하는지 확인

핵심 테스트 한두 개를 골라, 구현을 일부러 망가뜨리면 실패하는지 본다.

- 파일을 고칠 수 있으면: 구현 한 줄을 바꿔 테스트를 돌리고, 원래대로 되돌린다 (`git diff`가 비었는지 확인).
- 읽기만 할 수 있으면: 어떤 변경에서 어떤 단언이 실패할지 코드로 따라가고 "(코드 기준)"이라고 쓴다.

## 4. 판정

**blocking**

- 새 동작에 그 동작을 검증하는 테스트가 없다.
- 완료 기준의 근거로 든 테스트가 구현이 틀려도 통과한다.
- 새 테스트의 주된 단언이 호출 순서 전체나 결과 구조 전체를 고정해서, 동작이 같은 리팩터링에도 깨진다.
- 테스트를 지우거나 skip해서, 또는 기대값을 결과에 맞춰 통과시켰다.

**suggestion**

- 이름, 순서, 준비 코드 중복, 보조 단언의 과한 고정.

## 5. 보고

첫 줄: 본 범위와 건수(blocking N, suggestion N, 기존 부채 N). 점검 모드면 테스트 이름만 읽었을 때 흐름이 보였는지 한 문장으로 적는다.

항목마다:

- **제목**: 결과로 쓴다. ("요청 9개의 순서를 고정해서 blob 업로드를 병렬로 바꾸면 깨진다")
- 위치: `파일:줄`과 테스트 이름.
- 무엇이 문제인지: 어떤 변경에서 잘못 깨지거나, 어떤 버그에서 잘못 통과하는지.
- 방향: 무엇을 단언하면 되는지 한두 문장.
- 등급.

## 하지 말 것

- 커버리지 숫자만 보고 판단하기.
- 테스트가 많다는 이유로 좋다고 하기. 같은 것을 여러 번 고정하면 유지보수 비용만 는다.
- 스냅샷 갱신이나 기대값 수정을 "테스트 고침"으로 받아들이기.
